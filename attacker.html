Cross-site initiator

This page must be served from a different registrable domain than the victim lab (GitHub Pages is on the Public Suffix List, so *.github.io is its own site). Seed cookies at /setup on the victim origin first, then run each gesture below and watch the victim's /log.

STOP — this page is same-site with the victim.

Every result below will show Strict cookies being sent, and every one of them will be a false positive, because a same-site initiator is supposed to send them. SameSite compares registrable domains, so a different subdomain or a different path on the same host does not help. Serve this page from a different registrable domain.

A · Control — plain link click

Open victim /probe (normal click)

LEFT CLICK / TAP Expected: strict NOT sent, Lax sent. If Strict appears here, something is wrong with your setup — fix that before trusting any result below.

B · iOS / iPadOS Safari — long-press link preview

Long-press me to preview

TOUCH & HOLD → preview popover The popover performs a real page load. If the victim log shows STRICT SENT for this tag, that is the bug. Do not tap through to open — dismiss the popover, the request has already been made.

Long-press → Add to Reading List

TOUCH & HOLD → Add to Reading List Reading List saves an offline copy, which means a background fetch of the URL from a cross-site context. Separate code path from the peek; test it separately.

Long-press → Download Linked File

TOUCH & HOLD → Download Linked File Context-menu download of a cross-site link. Check the log entry's cookie list.

C · macOS Safari — force-click preview

Force-click me to preview

FORCE CLICK (one finger, press firmly) OR THREE-FINGER TAP Requires a Force Touch trackpad. If three-finger tap does nothing, set System Settings → Trackpad → Point & Click → "Look up & data detectors" to Tap with three fingers.

Right-click → Add Link to Reading List

RIGHT CLICK → Add Link to Reading List Then open the Reading List sidebar; the offline archive fetch may be deferred until the item is first shown. Watch the log across both moments.

Right-click → Download Linked File

RIGHT CLICK → Download Linked File Ties directly into download-origin handling.

Right-click → Open Link in New Tab

RIGHT CLICK → Open in New Tab Control case: this is still a cross-site initiation, so Strict must stay blocked. If it leaks here too, the bug is much broader than previews.

D · Cross-app initiation (strongest cross-site story)

Copy this link into Mail / Messages / Notes

SEND TO YOURSELF → TOUCH & HOLD Peek-and-pop is a system behaviour, not a Safari one. A link previewed from an attacker-sent email or message has no same-site relationship to the victim at all, which makes the "the initiator was cross-site" argument unarguable at triage.

E · Side effects worth measuring

Preview me, then check the jar

Does a Set-Cookie returned during a preview persist into the real cookie jar? If yes that is cookie forcing / session fixation, a second finding.

Preview me (service worker)

Can a previewed page register a service worker? That converts a transient preview into persistence on the victim origin.

Preview me, dismiss immediately

Response is delayed 5s. Dismiss the popover at once. If the log still records the hit, the server-side side effect happens whether or not the user ever sees the page — that kills the "but the user chose to preview it" counter-argument.

Preview me (victim → cross-site redirect)

Does the preview follow a redirect off the victim origin, and does the attacker origin receive the resulting request?

F · Escalation — authenticated secret exfiltration

Preview me (OAuth-style code theft)

/authorize mints a secret only if the Strict cookie arrives, then 302s it to a redirect_uri on this attacker origin. This is the difference between "blind GET CSRF" and "attacker reads an authenticated secret" — and the difference between a courtesy payout and a real one.
